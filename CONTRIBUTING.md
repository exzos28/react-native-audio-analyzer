# Contributing

Contributions are always welcome, no matter how large or small!

We want this community to be friendly and respectful to each other. Please follow it in all your interactions with the project. Before contributing, please read the [code of conduct](./CODE_OF_CONDUCT.md).

## Repository layout

This is a [Yarn workspaces](https://yarnpkg.com/features/workspaces) monorepo driven by [Turborepo](https://turbo.build):

| Path | What it is |
| --- | --- |
| [`packages/react-native-audio-analyzer`](packages/react-native-audio-analyzer) | The published library. |
| `…/src` | TypeScript API, Nitro specs (`src/specs/*.nitro.ts`) and Jest tests. |
| `…/cpp` | Platform-independent C++ core and the Nitro binding, plus host unit tests in `cpp/tests`. |
| `…/ios`, `…/android` | Platform code (`load()` downloader) and build files. |
| `…/libs/miniaudio` | [miniaudio](https://github.com/mackron/miniaudio) as a git submodule. |
| [`apps/rn-cli-example`](apps/rn-cli-example) | Bare React Native CLI app. |
| [`apps/expo-example`](apps/expo-example) | Expo development build app. |
| [`apps/docs`](apps/docs) | Documentation site (Docusaurus), deployed to GitHub Pages. |

Both apps depend on the library through `workspace:*` and resolve it from TypeScript sources, so JS changes show up without a build step. Native changes need a rebuild of the app.

## Setup

```sh
git clone --recurse-submodules https://github.com/exzos28/react-native-audio-analyzer.git
cd react-native-audio-analyzer
yarn            # Yarn 4 via Corepack: `corepack enable` if `yarn` is missing
yarn nitrogen   # generate the Nitro bindings (not committed)
```

Already cloned without `--recurse-submodules`? Run `git submodule update --init`.

> Use Yarn, not npm: the workspaces rely on Yarn.

Run **Nitrogen** (`yarn nitrogen`) again whenever you change a `*.nitro.ts` file.

## Running the example apps

### React Native CLI

```sh
yarn workspace rn-cli-example pods     # iOS only: bundle install + pod install
yarn workspace rn-cli-example start
yarn workspace rn-cli-example ios      # or: android
```

To edit native code in an IDE, open `apps/rn-cli-example/ios/AudioAnalyzerExample.xcworkspace` in Xcode (sources are under `Pods > Development Pods > AudioAnalyzer`) or `apps/rn-cli-example/android` in Android Studio.

### Expo (development build)

```sh
yarn workspace expo-example ios        # or: android — runs prebuild, builds and installs
yarn workspace expo-example start      # Metro for the dev client
```

The `ios/` and `android/` folders of the Expo app are generated by `expo prebuild` and are not committed.

## Documentation site

```sh
yarn workspace docs start   # http://localhost:3000/react-native-audio-analyzer/
yarn workspace docs build   # what CI runs; fails on broken links
```

The API reference is generated from the TSDoc comments in `packages/react-native-audio-analyzer/src` — document public API there. Waveforms on the site are rendered at build time from real analyses stored in `apps/docs/examples` (see the README there); regenerate them with `yarn workspace docs examples:analyze` (needs CMake) after changing the C++ core.

The site is deployed by the [Docs workflow](.github/workflows/docs.yml) on every push to `main` that touches it. It needs GitHub Pages enabled with **Source: GitHub Actions** in the repository settings.

## Checks

```sh
yarn lint        # ESLint + Prettier for the whole repository (`yarn lint --fix` to fix formatting)
yarn typecheck   # TypeScript in every workspace
yarn test        # Jest: library unit tests and app integration tests
yarn test:cpp    # C++ core tests with AddressSanitizer + UBSan (needs CMake and a C++20 compiler)
                 # on macOS this includes the AudioToolbox platform decoder
sh packages/react-native-audio-analyzer/cpp/tests/run-android.sh
                 # the same tests on a connected Android device/emulator (MediaCodec decoder)
```

CI runs all of the above and also builds both apps for Android and iOS.

Please add tests with your change:

- JS API and helpers: `packages/react-native-audio-analyzer/src/__tests__`.
- C++ core: `packages/react-native-audio-analyzer/cpp/tests`. These run on your machine without a device, so prefer putting logic into the platform-independent core.

## Changesets and releases

Releases are automated with [Changesets](https://github.com/changesets/changesets). If your pull request changes the published package, add a changeset:

```sh
yarn changeset
```

Choose `patch`, `minor` or `major` and write a user-facing summary. It ends up in the changelog and the GitHub release.

After merge, the [Release workflow](.github/workflows/release.yml) opens or updates a **"chore: version packages"** pull request that bumps the version and updates `CHANGELOG.md`. Merging that pull request publishes the package to npm (with provenance) and creates a GitHub release. Publishing uses [npm trusted publishing](https://docs.npmjs.com/trusted-publishers) (OIDC), so there is no npm token secret: the package's trusted publisher on npmjs.com is this repository's `release.yml` workflow.

## Commit message convention

We follow the [conventional commits specification](https://www.conventionalcommits.org/en):

- `fix`: bug fixes, e.g. fix crash due to deprecated method.
- `feat`: new features, e.g. add new method to the module.
- `refactor`: code refactor, e.g. migrate from class components to hooks.
- `docs`: changes into documentation, e.g. add usage example for the module.
- `test`: adding or updating tests.
- `chore`: tooling changes, e.g. change CI config.

[Lefthook](https://github.com/evilmartians/lefthook) runs ESLint and TypeScript on commit and validates the commit message.

## Sending a pull request

> **Working on your first pull request?** You can learn how from this _free_ series: [How to Contribute to an Open Source Project on GitHub](https://app.egghead.io/playlists/how-to-contribute-to-an-open-source-project-on-github).

- Prefer small pull requests focused on one change.
- Verify that linters and tests are passing.
- Add a changeset if the package changes.
- For pull requests that change the API or implementation, discuss with maintainers first by opening an issue.
